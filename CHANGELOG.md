# Changelog

## 0.9.0 — 2026-10-17

- **Published to npm as `@cleocode/goal`.** The package was `opencode-goal` (private, installed from git tags). It is now public with npm provenance. The plugin id stays `opencode-goal`, so existing configs, state and the TUI keep working. A tag-triggered `release.yml` publishes through npm Trusted Publishing (OIDC, no token).
- **The bin runs on plain Node.** `cleo-goal` and `ocg` point at `dist/cli.js`, a Node bundle built from `cli/ocg.ts` by `scripts/build-cli.mjs` and committed like `dist/tui.js` (CI fails when it is stale). The tick, status and install paths no longer use Bun APIs: git and owner check commands run through `node:child_process`, the Stop payload is read from `process.stdin`, and goal contracts parse with the `yaml` package when Bun's built-in parser is absent (OpenCode still uses Bun's).
- **`cleo-goal --version`, `status --json` and `install --project`.** The contract CLEO reads (`schemaVersion: 1`). `install --project [--spec] [--json] [--dry-run]` writes only the project's `.opencode/opencode.json` (`plugins`), is idempotent, replaces an older spec of this plugin in place (keeping its options), and refuses the home directory, user-global config, invalid JSON and a `.jsonc` config without writing. A `.opencode` dir or `opencode.json` symlinked into `~/.config`, `$XDG_CONFIG_HOME`, `~/.opencode` or anywhere outside the project is refused; a symlinked `opencode.json` inside the project is written through.
- **CI.** Typecheck, unit tests, the scripted-harness test under Bun and Node, and a packed-bin smoke on a PATH without Bun, on every push and pull request.

## 0.8.1 — 2026-10-17

- **The post-goal summary is scannable (T120).** The summary dialog now opens with a 3–5 second digest — `completed`, `WENT RIGHT`, `WENT WRONG`, `STILL OPEN`, `NEXT`, linked tasks, and a one-line provenance split (`host 6 · verifier 2 · owner 1`) — capped at 14 lines; the full report (criteria, non-goals, findings) stays in `text`. Palette actions use Title Case. The RPC summary event carries `title` and `digest`.
- **A pending decision is asked once, then silent (T121/T123).** `shouldReaskDecision()` is now a pure policy: stale wins, an open form never duplicates, a dismissed (`interrupted`) review never re-asks, and an already-asked review never re-asks. The once-per-process marker lives at module scope, so a plugin re-setup cannot silently ask again; a real process reload clears it and re-presents once. `restorePendingDecision()` recovers the latest pending decision after a reload.
- **Fixed — an explicit review request restores a dismissal.** The once-per-process marker also blocked the documented `goal_review` restore path, because the direct ask is skipped while the session is mid-turn and the deferred re-ask was suppressed. `reviewDecision` now clears the marker for that exact decision; the protected `durable-goal-decisions` oracle caught it before release.
- **The loop prefers leaves over epics (T122/T123).** `readyCleoTask()` asks `cleo next -n 5`, skips sagas/epics, and returns the first leaf; skipped parents are journalled as `continue-parent-skipped`. If only parents are ready, the loop treats it as no work instead of opening a goal for a rollup. The design note records the work-vs-state rule.
- **Recorded.** CLEO lifecycle records for T119/T122 are committed with the fixes; T001 stays closed with `docs/cleo-t001-completion.md` as its one-off receipt.
- **Release posture.** A git-tag patch only. **Nothing was published to npm.**

## 0.8.0 — 2026-10-17

- **A clean restart resumes by itself (C1).** A host restart no longer asks for a click when the lock is unchanged and the run is intact: the run re-arms its wait, re-verifies a claim it was verifying, or receives the continuation it had pending. A contract changed under the run, a repaired/divergent run and an interrupted write still pause and name the cause. The decision is the pure `restartDecision` (`src/engine/interrupt-policy.ts`).
- **An accepted amendment resumes in the same act (C2).** Acceptance previously left the run paused at "owner accepted amendment; resume when ready", so every amendment cost a second owner decision. It now clears the pause, records `resumed` + `amendment-resumed`, and admits the ordinary continuation with no new question — through both the native review and genuine Composer chat. A recovered acceptance (host died after the commit) resumes on reload.
- **A stale decision is never re-presented (C3).** Answered, expired, superseded and generation-changed reviews are silenced with a `decision-silenced` ledger event; only a dismissed (`interrupted`) review is still unanswered and may be restored. `goal_review` refuses a stale review instead of minting a replacement.
- **Completion starts the next ready CLEO item by itself (C4).** `cleo next` → `cleo show --full` → a contract generated from the task's own acceptance (verifier criteria), linked back to the task id, then a fresh session and a real run. The start is a notification plus `continue-work` ledger events; no completion decision is created. A project with no ready item keeps today's behaviour.
- **Idle availability announcements over AgentMBX (C5).** One outstanding announcement at a time, a 15-minute cooldown floor, bounded reply polling, and replies recorded as candidate work (never consent). The channel is injectable/off by default (`OCGOAL_PEER_IDENTITY`); tests use a fake `agentmbx` and touch no network.
- **The stop rules are a tested policy (C6).** Human criteria, blockers and outward/destructive acts always stop. A first visit to a new project and an exhausted budget also stop, with explicit contract opt-outs (`autonomy.visit_new_projects`, `autonomy.continue_past_budget`). The contract's stated intent reads the opposite for those two; that contradiction is recorded in the design note rather than silently resolved.
- **A fresh launch carries a handoff (D1).** `handoff.md`/`handoff.json` beside the contract, built from the host's own facts — prior run, lock, red baseline, HEAD/branch/dirty state, first plan step, authority vs stale docs — and a bounded digest in the turn-1 kickoff. It is labelled context, not authority. This was the first `fresh: true` launch in 22 launches; the prior 21 started inside the session that already knew everything.
- **An unknown check key fails validation (D6).** `expect.stderr_contains` used to be silently dropped and defaulted to `exit: 0`, weakening a criterion to "the command exited". Unknown expectation keys are now errors naming the key and the supported set.
- **Documentation.** `docs/research/proactive-continuation.md` states the sources and order, the announcement rate limit, the stop rules, what is never automatic, and the release posture; `docs/research/session-handoff.md` diagnoses the fresh-launch gap; `docs/HANDOFF-v0.8.0.md` is the session handoff.
- **Release posture.** A new minor, published as an immutable git tag and installed from it. **Nothing was published to npm.**

## 0.7.1 — 2026-10-16

- **The tick no longer crashes on an unreadable store (T102).** v0.7.0 named the payload and transcript degradations but left the *store* half unguarded: `ocg tick` read the goals directory and `run.json` with no `try/catch`, so an I/O error (permissions, `ENOTDIR`) escaped as an exception. Empty stdout means "no live goal" to the harness dispatcher, so a crash was indistinguishable from "nothing to do" — which silently **drops** the run and ends the session. An unreadable store, run record or contract is now a stated degradation: the tick logs what it could not read and **holds** the session (`{"final":false}`) rather than printing nothing on a guess, and a record it cannot read is never replaced by an invented one. A readable live run beside an unreadable record is still ticked, and the unreadable record is named.
- **The bin survives an unexpected throw (T102).** `ocg tick` catches an error from the tick, holds the session and puts the reason on stderr, instead of dying with an empty stdout.
- **C1's suite now covers the store clause (T102).** `test/unit/tick-record.test.ts` gains the absent-store, empty-store, unreadable-store, unreadable-record, unreadable-record-beside-a-live-run, unreadable-contract, unparsable-contract and "wrote nothing on degradation" cases.
- **Why this is a patch and not a re-cut (T102).** v0.7.0 was tagged and pushed, and then this defect was found by *this goal's own C1* before v0.7.0 was ever loaded into a session. The fix is published **forward** rather than rewriting the published v0.7.0 tag, because the tag is public history and immutability is exactly what C5 demands. C5's check is a `--min-version 0.7.0` floor and C6 is written for the `v0.7.x` line, so the v0.7 release this goal loads is v0.7.1. Nothing was published to npm.

## 0.7.0 — 2026-10-16

- **The tick RECORDS the turn (T102)** — `ocg tick` no longer decides from a frozen run state. Before deciding it advances the turn, recomputes the repository fingerprint (a move counts as progress), honours a claim the run already carries, and — best-effort and optional — mines a transcript the harness Stop payload points at for tool calls and a progress call. Everything is written through OCG's own store, so the records, the ledger and the schema stay identical to the adapter's, and the stall pause, recovery, the budget wrap-up and the blocker repeats now work under a harness that is not OpenCode.
- **It runs the verification of a claim (T102)** — a claim sets the run to `verifying`, the tick runs the host checks, records the results and the verdict, and either completes the run (printing nothing, so the harness session can end) or hands the agent the verdict as its next continuation. A goal whose verification is host-only can therefore be driven to `complete` from another harness; a goal asking for the independent verifier child still needs the OpenCode adapter, and the note says so.
- **`ocg claim` (T102)** — the agent-side claim surface for a harness with no OCG tools: it records a claim on the live run through OCG's own store, so the next tick can verify it. (OpenCode agents keep using the `goal_claim` tool.)
- **Honest degradation, named rather than guessed (T102)** — a missing or non-JSON Stop payload, a payload naming no transcript, an unreadable transcript and a transcript with no content are each logged as `could not see …` to stderr, and the turn is still recorded with the fingerprint the tick can take. It never invents a tool call, a progress call or a live-check transition.
- **Proven by a scripted harness (T102)** — `test/host/tick-scripted-harness.test.ts` drives a real goal from kickoff to `complete` using only the bin: the harness ticks, a scripted agent does the work and claims through `ocg claim`, and the next tick verifies and completes. No OpenCode anywhere.
- **Naming (owner decision)** — the package becomes `@cleocode/goal` ("CLEO Goal") with the bin `ocg`, documented as "open cleo goal", and `cleo-goal` as an equally supported long form, so CLEO's default `ocg tick` keeps working. The rename and the Node-runnable bin are the packaging goal that follows; nothing was published here (an `npm pack --dry-run` only).

## 0.6.0 — 2026-10-16

- **The loop's decision is a pure function (T102)** — `decide(state, signals, limits) -> action` now lives in `src/engine/loop.ts` with no filesystem, network or OpenCode types, and the OpenCode adapter *applies* its action instead of holding the logic. Every case the adapter took is pinned by `test/unit/loop-decision.test.ts` (a claim beats a continuation; the wrap-up turn precedes the budget stop; a stall precedes the ordinary continuation; the owner-set `on_stall` policy in both directions; the wait deadline arithmetic; recovery selection), and the existing goal-loop suites prove the adapter's behaviour is unchanged.
- **An `ocg` bin with a `tick` subcommand (T102)** — it implements CLEO's merged Stop-dispatcher contract (`#2306`) exactly: the harness Stop JSON on **stdin**, **JSON only on stdout** (`{"decision":"block","reason":…}` to keep the agent working, `{"final":false}` to hold the session), every log line on **stderr**, and **nothing at all** when there is no live goal or no `.opencode/goals`. The reason is the **same continuation** `renderTailNote` produces for the decided `TailKind`, so a harness driven through tick behaves identically to OpenCode for the decision it makes. It is read-only, and it deliberately does **not** install its own Stop hook — CLEO's dispatcher owns Stop.
- **The parity is documented (T102)** — `docs/research/harness-agnostic-loop-decision.md` carries the decision contract, the case-by-case parity table against the adapter, and an honest statement of what the tick does not do yet (it does not advance turn counters or the stall streak).
- **npm publication metadata prepared (T102)** — a `bin` entry for `ocg` and the `cli` folder in `files`. **Nothing was published**: no `npm publish`, no registry credential, and the package is still installed from a git tag.
- **Fixed** — the tick first treated `archived` as a terminal status, which is not one of the run states; it now uses the real terminal set (`complete`, `failed`, `aborted`, `superseded`), so a failed or superseded goal is not mistaken for a live one.

## 0.5.2 — 2026-10-16

- **The dogfood cache is bound to the SERVING ENGINE (T102)** — the reuse key now hashes the serving pid, location and endpoint alongside the release SHA and the artifact hashes. A record produced by a different (restarted or replaced) engine is never reused, which is what silently broke the manager flow: the v0.5.1 chain reused an interview record from pid 24041 after the server had moved to pid 30270, so the manager driver refused with `QA serving PID changed` before it could exercise anything. A cache that cannot be reused is now labelled `stale-cache` **by name**, with `cacheMismatch` reporting whether it was the release, the artifacts or the engine that changed — and that label now takes precedence over the generic incomplete-flow label, because the mismatch is the root cause.
- **An export↔task coherence check (T102)** — `bun scripts/dogfood-t102-coherence.ts` fails when the export's manager verdict and CLEO task T102 disagree in either direction: a task closed while the manager flow did not pass would be a closure on a technicality, and a manager pass with the task still open would be an unrecorded result.
- **A multi-task goal's contract states the commit-citation rule (T102)** — when a goal links more than one CLEO task, the rendered contract requires every run commit to cite **all** of them (e.g. `feat(T123,T124): …`), because the work lands on `main` with no PR or task branch and `cleo done --commit <head>` binds a task only if its message cites it (CLEO PR #2305). Without it the uncited tasks stay open with a "neither cites" blocker.
- **Per-flow export detail now names the endpoint too** — each flow's section gives the serving pid, location and endpoint it actually ran against, next to the release SHA and artifact hashes.

## 0.5.1 — 2026-10-16

- **A consolidated exact-release real-model dogfood workflow (T102)** — `scripts/real-model-dogfood.ts --assert` runs the five existing native flows (interview/handoff, manager, lifecycle, completion, amendment) against the **installed** release in one bounded pass, records for each the exact release SHA, the serving PID and location, the model/agent selections and the server/UI/skill artifact hashes, preserves the bounded raw owner messages, forms and tool calls, and labels every flow **honestly**: `pass`, `fixture`, `stale-cache`, `partial` or `timeout`. ## 0.4.7 — 2026-10-16

- **An owner resume during a busy turn takes effect immediately and exactly once (T091)** — pausing (or resuming) left the run's previous `wait` in place, so an immediate busy resume was resurrected into `waiting` at the turn's end and never received its continuation: the run looked resumed but was stranded. Pause and resume now clear the obsolete wakeup and wait, a resume is idempotent (an already-running run journals no second receipt and is not admitted twice), and exactly one continuation is admitted when the busy turn ends. The deferral carve-outs are unchanged: a resume behind a pending native form, a cross-session target, a terminal run or worker-sent consent still defers or refuses.
- **A waiting goal's claim or expired wait drains exactly once behind a busy turn (T092)** — a wait that expires while an owner turn is running still wakes exactly once afterwards, and a claim that ends a wait cancels the obsolete wakeup, so the old deadline does not verify or admit again.

## 0.4.5 — 2026-10-15

- **A late goal_verdict is still an answer (T108)** — a verifier that calls `goal_verdict` just after the per-round budget was recorded as "did not call goal_verdict" and the round thrown away. There is now a short grace window after the budget, and if the call is in the captured transcript it is used (`verifier-fallback`, ledger `from: "transcript"`). - **Reading goal state is not writing it (T108)** — the new write guard was too broad: a shell command that merely read the run state through an interpreter (`open('<path>')` with no write mode) was refused. ## 0.4.3 — 2026-10-15

- **Every write path into a live goal folder is refused (T108)** — the guard covered edit/write/patch only, so an agent hand-merged `run.json` with a shell command (the reported file had duplicate `updatedAt`, `tokens`, `tools` and `lastUsageEmit` keys). Shell commands and scripts are now checked too — redirection, `tee`, `sed -i`, `mv`/`cp`/`rm`/`truncate`, and interpreters that write the path — and every refusal names the supported tool: `goal_progress`, `goal_wait`, `goal_block`, `goal_flag`, `goal_claim`, `goal_manage`, `goal_recover_divergence`. Reads still work, and another project's or an archived folder is unaffected.
- **A corrupt run.json is proven, not guessed (T108)** — duplicate JSON keys are found by scanning the raw bytes, because `JSON.parse` silently keeps the last value. The run is then rebuilt from its own ledger `start` event and its locked contract snapshot (raw bytes kept beside the run as `run.json.corrupt-<ts>.json`, with `run-state-corruption` and `run-state-repaired` events); when those cannot prove the identity, the goal is refused and left to the owner instead of guessing.
- **Stalling stops punishing real work (T108)** — host-visible activity is recorded per turn, a `goal_progress` note counts as progress, and the stall reason says whether the run was active or idle. An owner-set `autonomy.on_stall: continue` keeps a stalled-but-active run going with a recorded `stall-report` instead of pausing; the default stays `pause`, and an idle run still stops. `run.json` keeps being written by the engine alone.
